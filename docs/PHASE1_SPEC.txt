這個專案最適合做成一個「**組織模擬器 + 管理決策遊戲 + emergent storytelling engine**」，而不是傳統的數值經營遊戲。

真正能讓它站出來的，不是「AI 生成 Slack」本身，而是：**公司內部先有一個可信、可重播、可驗證的世界真相，然後 Slack、Email、會議、董事會紀錄與人物行為只是這個世界真相的不同視角。**

---

# 1. 產品核心玩法

我建議先把產品暫時定義為：

**AI Company Simulator**

玩家不是直接控制員工，而是扮演 CEO / Founder。

你的權力很大，但不是全知全能。

你可以決定：

- 招募與解僱
- 薪資與升遷
- 組織架構
- 公司策略
- 產品方向
- 客戶策略
- 融資
- 部門預算
- 工作強度
- 公司文化
- 是否冒險
- 是否擴張

但玩家**不能直接指定某個員工的感受與行為**。

例如你不能按：

> CTO 忠誠 +20

你只能：

> 給 CTO 加薪  
> 拒絕 CTO 的產品提案  
> 空降一名 VP Engineering  
> 讓 CTO 管 25 人  
> 要求團隊連續 Crunch 三個月

模擬系統再決定：

```text
信任下降
↓
壓力增加
↓
CTO 與 VP 關係惡化
↓
開始考慮離職
↓
偷偷接觸獵頭
↓
幾名核心工程師受到影響
↓
可能形成集體離職事件
```

這才是遊戲。

## 最重要的核心 Loop

```text
觀察公司
   ↓
發現問題 / 機會
   ↓
做管理決策
   ↓
時間推進
   ↓
員工 / 客戶 / 市場反應
   ↓
產生新的資訊
   ↓
玩家重新判斷局勢
```

建議時間尺度：

```text
1 simulation tick = 1 天

玩家通常：
推進 1 天
推進 1 週
推進到下一事件
```

部分系統每天跑。

部分系統每週跑。

財務、薪資、KPI 等則月結。

# 2. 最重要的產品差異化

不要把賣點定義成：

> 「AI 幫你生成公司 Slack。」

這很容易變成 gimmick。

真正的差異應該是：

## 「公司裡的每個人，都不是你的棋子。」

例如員工 Alice：

```yaml
name: Alice Chen

role: Senior Engineer

skills:
  engineering: 82
  leadership: 46
  sales: 8

traits:
  ambition: 77
  loyalty: 43
  riskTolerance: 61
  sociability: 35

state:
  stress: 68
  satisfaction: 51
  burnout: 31

expectations:
  salary: 115000
  promotion: high

relationships:
  Bob: +63
  CTO: -41
```

但這還不夠。

她還要有：

```text
記憶
目標
職涯期待
公司觀感
對其他人的觀感
近期事件
```

比如：

```text
2028-03-12
CEO 拒絕 Alice 的 promotion request

2028-05-04
Alice 被要求負責失敗專案

2028-07-21
Alice 的好友 Bob 離職

2028-09-02
Alice 收到 competitor interview
```

最後：

```text
Alice resignation probability:
8% → 12% → 28% → 61%
```

真正吸引人的體驗會是：

> 「等等，Alice 為什麼辭職？」

然後玩家一路追查她過去兩年的歷史。

這會形成類似 Football Manager 的人物故事。

---

# 3. 遊戲的另一個關鍵：Information Asymmetry

這個系統非常重要。

玩家不應該直接看到：

```text
Alice loyalty = 32
Alice resignationChance = 71%
```

那會直接變 Excel simulator。

玩家看到的應該是：

```text
Manager report:
Alice 最近似乎比較沉默。

Slack:
Alice 已經兩週沒有在 #engineering 分享更新。

Performance review:
Strong performer.

HR note:
Promotion expectations may not be aligned.

1:1 summary:
"I'm fine."
```

真正數值在 simulation state：

```text
loyalty = 32
stress = 73
promotionExpectation = 82
exitIntent = 61
```

這樣玩家是在「管理人」，不是在管理數字。

# 5. Deterministic vs LLM

這一條應該成為整個專案的最高架構原則。

| 系統 | Deterministic | LLM |
|---|---:|---:|
| 財務 | ✅ | ❌ |
| 薪資 | ✅ | ❌ |
| 收入 | ✅ | ❌ |
| burn rate | ✅ | ❌ |
| 員工能力 | ✅ | ❌ |
| 工作產出 | ✅ | ❌ |
| 壓力 | ✅ | ❌ |
| burnout | ✅ | ❌ |
| 忠誠 | ✅ | ❌ |
| 離職判定 | ✅ | ❌ |
| 關係變化 | ✅ | ❌ |
| 客戶 churn | ✅ | ❌ |
| 市場需求 | ✅ | ❌ |
| 產品品質 | ✅ | ❌ |
| Competitor 行為 | ✅ / policy | 可選 |
| Agent 高階決策 | ✅ fallback | 可選 |
| Slack 文案 | template fallback | ✅ |
| Email | template fallback | ✅ |
| Wiki | template fallback | ✅ |
| 董事會文字 | template fallback | ✅ |
| 人物對話 | template fallback | ✅ |
| 公司新聞 | template fallback | ✅ |
| 世界真相 | ✅ | **絕對禁止** |

例如：

Simulation：

```json
{
  "event": "employee_resigned",
  "employee": "alice",
  "reasonWeights": {
    "compensation": 0.17,
    "management": 0.41,
    "burnout": 0.29,
    "career": 0.13
  }
}
```

LLM 只能把它變成：

> Alice 表示，過去幾個月她逐漸對團隊方向感到失望，同時長期高壓工作讓她開始重新評估自己的職涯。

LLM **不能決定 Alice 是否辭職**。

# 6. RNG 設計

不要在任何 simulation code 裡出現：

```ts
Math.random()
```

建立：

```ts
interface RandomSource {
  next(): number;
  int(min: number, max: number): number;
  chance(probability: number): boolean;
  pick<T>(items: readonly T[]): T;
}
```

所有 randomness：

```text
GameSeed
 ↓
RandomManager
 ↓
named streams
```

例如：

```text
employees
market
customers
events
competitors
recruitment
relationships
```

避免某個 UI 修改導致整個世界 RNG sequence 改變。

最好採：

```text
rootSeed
+
system
+
entityId
+
date
+
operation
```

導出 deterministic random。

# 7. Simulation Architecture

Simulation 不應該是一個：

```ts
updateEverything()
```

而是 scheduler。

例如：

```text
DAY START
│
├─ EmployeeStateSystem
├─ WorkSystem
├─ RelationshipSystem
├─ CustomerSystem
├─ ProductSystem
├─ MarketSystem
├─ CompetitorSystem
├─ EventSystem
├─ InformationSystem
│
└─ DAY END
```

每 7 天：

```text
WeeklyPlanningSystem
ManagerSystem
RecruitmentSystem
CultureSystem
```

每月：

```text
PayrollSystem
FinancialCloseSystem
InvestorSystem
PerformanceSystem
```

系統排序必須固定。

例如：

```ts
const DAILY_SYSTEMS = [
  employeeStateSystem,
  workSystem,
  relationshipSystem,
  productSystem,
  customerSystem,
  marketSystem,
  eventSystem
] as const;
```

不能依賴 object iteration 順序或 async completion 順序。

# 9. Relationship Model

Relationship 不要存在 employee 裡面。

使用：

```ts
interface Relationship {
  sourceId: EmployeeId;
  targetId: EmployeeId;

  trust: number;
  respect: number;
  affinity: number;
  rivalry: number;
  resentment: number;
}
```

而且：

```text
Alice → Bob
```

跟：

```text
Bob → Alice
```

不是同一筆。

所以可能：

```text
Alice respects Bob = 80
Bob respects Alice = 35
```

這才能形成有趣組織政治。

# 10. Memory System

每個 Agent 不應保存全部歷史。

使用有限記憶：

```ts
EmployeeMemory {
  id
  date

  type

  entities

  emotionalImpact

  importance

  sentiment

  decayRate
}
```

例如：

```text
PromotionRejected

importance: 90
sentiment: -80
decayRate: 0.01
```

而：

```text
CEO praised employee
importance: 25
decayRate: 0.08
```

長時間後慢慢失去影響力。

重大事件可以永久留下。

---

# 11. Agent Decision Architecture

每個 Agent 的決策最好分三層：

```text
Need
↓
Intent
↓
Action
```

例如：

```text
Need:
career growth

Intent:
seek promotion

Action:
ask manager
```

如果失敗：

```text
Intent:
explore external opportunities

Action:
accept recruiter interview
```

最後：

```text
Intent:
leave company

Action:
resign
```

這樣玩家才會感覺：

> 他不是突然 RNG 辭職。

# 12. Event Architecture

每件重要事件應該是 immutable domain event。

例如：

```ts
EmployeeSalaryChanged
EmployeePromoted
EmployeeResigned
ProductLaunched
CustomerWon
CustomerChurned
FundingRoundClosed
ConflictEscalated
TeamCreated
ManagerChanged
```

結構：

```ts
interface DomainEvent<T> {
  id: EventId;

  tick: number;
  date: SimDate;

  type: string;

  payload: T;

  causedBy?: EventId | CommandId;

  visibility: EventVisibility;
}
```

這會成為：

- replay
- debugging
- analytics
- storytelling
- save migration

的共同基礎。

# 20. 一個非常重要的 Scale Architecture

如果將來 10,000 員工：

絕對不能：

```text
10,000 agents × LLM
```

甚至不能每個 tick 都完整模擬每一個人。

應採：

```text
Level 1
Named Agents

CEO
executives
managers
key employees

high fidelity
```

```text
Level 2
Active Employees

medium fidelity
```

```text
Level 3
Workforce Cohorts

aggregate simulation
```

例如：

```text
Tokyo Engineering
412 employees

morale 71
turnover 8%
productivity 83
```

只有重要人物升格成 Named Agent。

這樣 5,000–50,000 人公司仍然能模擬。

# 22. Replay Architecture

這個專案應從 Day 1 做 replay。

保存：

```text
seed
+
initial config
+
player commands
```

理論上：

```text
InitialState
+
Commands
=
FinalState
```

驗證：

```text
hash(run(seed, commands))
===
hash(replay(seed, commands))
```

若不相同：

**測試失敗。**

這會救你未來大量 debug 時間。

---

# 23. State Hash

每 N ticks：

```text
canonical world state
↓
stable serialization
↓
SHA-256
```

例如：

```text
tick 100 = c102...
tick 200 = 899a...
tick 300 = 77da...
```

replay 時比較。

這可以非常快定位 deterministic divergence。

# 26. 測試策略

建議四層。

### Unit

# 40. 可直接交給 Codex 的 Phase 1 Prompt

# AI Company Simulator — Phase 1 Development Specification

You are beginning implementation of a new production-quality software project.

The project is not a prototype or throwaway demo.

The objective is to build a maintainable deterministic company simulation game that can eventually grow from simulating a 3-person startup into a multinational corporation.

The final product will be distributed as a Windows desktop application.

A private GitHub repository must be maintained throughout development.

---

# PRODUCT

Working title:

AI Company Simulator

Core fantasy:

The player is the founder / CEO of a company.

The player controls company-level decisions, but does not directly control employees.

Employees are autonomous simulated agents with:

- skills
- personality
- ambitions
- expectations
- stress
- satisfaction
- loyalty
- relationships
- career goals
- memories

The player's decisions indirectly affect employee behavior.

Example causal chain:

CEO rejects promotion request

→ employee career satisfaction decreases

→ trust in management decreases

→ employee becomes more receptive to recruiters

→ competing company makes offer

→ employee resigns

The player should experience these events as emergent consequences rather than scripted stories.

---

# NON-NEGOTIABLE ARCHITECTURE PRINCIPLES

The simulation must not depend on an LLM.

The entire game must work offline.

Do not use an LLM in Phase 1.

The simulation must be deterministic.

The same:

- seed
- initial configuration
- player commands

must produce exactly the same simulation result.

Never use Math.random() anywhere in simulation code.

All randomness must come through an injected deterministic RNG abstraction.

UI state and simulation state must be separate.

React components must never directly mutate simulation state.

All simulation modifications must happen through commands.

Do not create fake backend behavior or placeholder simulation systems merely to make the interface look functional.

The implementation must be maintainable and suitable for continuous iteration.

---

# TECH STACK

Use:

- TypeScript
- Node.js
- pnpm workspace
- Electron
- React
- Vite
- Zustand for UI state only
- Zod for runtime schema validation
- SQLite for persistence
- Vitest
- Playwright
- electron-builder
- Tailwind CSS
- Recharts where charts are appropriate

Simulation code must be framework-independent pure TypeScript.

The simulation package must run directly under Node without Electron or React.
